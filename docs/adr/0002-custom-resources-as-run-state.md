# 0002: Incidents and steps are custom resources

- Status: accepted
- Date: 2026-11-15

## Context

The triage controller kept runs in memory. A restart lost every run and the dedup window, so the same alert could start a second triage. With a coordinator in a separate process, the two components also need state they can both see.

## Decision

Two namespaced custom resources in `triage.k8s-agent-sandbox.io/v1alpha1` (`api/v1alpha1`, CRDs generated by `controller-gen` into `deploy/crds/`):

- `Incident` in `alert-triage`: one alert. The triage controller creates it; the coordinator owns its status (`Pending`, `Triaging`, `Done`, `Failed`).
- `TriageRun` in `agent-sandboxes`: one triage step. The coordinator writes its spec (alert, ServiceAccount, model, deadline, `suspend`); the triage controller writes its status (phase, sandbox, report, error, notified).

Each field has one writer. Step resources live in the sandbox namespace so the step's identity and Sandbox can carry owner references to them. Dedup finds earlier incidents by a fingerprint label, read uncached.

## Alternatives considered

- **A database or ConfigMap.** More moving parts, or no schema and no watch semantics. Rejected.
- **Incident and steps in one namespace.** Would put RBAC objects for agents next to the controllers, or Incidents next to sandboxes. Rejected.

## Consequences

- Runs and dedup survive restarts. `kubectl get incidents,triageruns -A` shows the system's state.
- The controllers use controller-runtime; the dependency is new.
- Reports are stored in `TriageRun` status, so they count against etcd object size (reports are capped at 256 KiB by the controller). Finished incidents and their runs are deleted after `INCIDENT_RETENTION`.
